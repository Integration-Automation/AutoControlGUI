## U-20261030-17 · 2026-10-30 · Keep a stubborn leftover from stopping the owner service, and never wait on a purge · #snapshot #agent #linux #security

- A fourth independent review verified MAJOR-A and the other third-review items
  fixed. It found one major problem, caused by the purge taint added in
  U-20261030-15: a single helper could make the guardian fail on every start.
  It could leave a payload-owned directory deeper than the descriptor limit,
  or one another ID wrote into. That tainted the slice, and the next start's
  purge tainted every slice. This is fixed here, with the review's minors and
  notes.
- **Purge.**
  - A removal that finds the object already gone counts as done.
  - A payload-owned object that cannot be removed is closed off (root, mode
    0), opened without following links and checked by inode before
    `fchown`/`fchmod`.
  - The walk is bounded to 64 open levels; an owned directory deeper than that
    is closed off whole.
  - Only an object that can be neither removed nor closed off taints, and only
    its slice.
  - A root that is a link is resolved once and used only if root owns the
    target and others may write it only when sticky.
  - The manifest may add roots (`purge_roots`).
- **Startup, waiting and shutdown.**

    once.
  - Choosing a slice never waits: with none free, there is no current epoch
    and clients wait in the listener's backlog until a purge or a retiring
    epoch ends.
  - A stop kills every epoch, then abandons running purges; the next start
    purges.
  - The purge child closes every inherited descriptor (journal lock, listener,
    channels), dies with the guardian and unblocks signals.
- **Limits and accounts.**

    `subtree_memory_max`), and `records` gets `cgroup.max.depth` 32.
  - Every payload ID of every range is one account for the connection share.
  - The guardian's accept rate is per listed client entry.
  - A connection is kept active only after its frame authenticated.

  group must be the service's socket group. The service's IDs must lie
  outside every payload range. The example payload range moves to 50000.

## U-20261030-20 · 2026-10-30 · Recognise the quarantine by inode, rerun short purges, and retry starts from the main loop · #snapshot #agent #linux #security

- A sixth independent review confirmed MINOR-B, NOTE-D…H and the routing half
  of NOTE-11 fixed, and MINOR-C's residual risk acceptable. It found two major
  problems:
  - **M1.** The quarantine used a fixed name. Any local user who took that name
    first turned the U-20261030-19 fix back into close-off in place. The walk
    also skipped that name whoever owned it, so a payload could hide files in a
    directory with that name.
  - **M2.** A refused epoch creation looped straight back into a retry without
    polling. Once the crash backoff aged out, the guardian spun at full CPU and
    never read SIGTERM.
- **Quarantine.**
  - It is made when first needed, under a random name.
  - It is recognised by inode, never by name; a name someone else took first is
    just another directory to walk.
  - An emptied quarantine is removed, and so is an emptied directory inside
    one. Earlier quarantines are walked and removed once empty.
  - Closing off sets mode 0 before changing the owner (N1). Identity checks
    compare the owner too, and a failed move back is logged (N2).
- **Short purges.**
  - One root's purge reads at most 4,194,304 entries (m2). A purge stops short
    when it hits that budget, runs out of quarantine passes, or has no
    quarantine when it needs one; that purge reports itself incomplete (m4).
  - An incomplete purge runs again, after a one-second pause, before its slice
    is handed out; startup purges that stopped short continue in a child.
  - Directories deferred during quarantine passes are walked in the same pass
    (m3).
  - Payload files a payload put inside another ID's directory, beyond that
    budget or past 256 deep directories, are logged, not tainted. Leaving them
    needs that ID's cooperation.
- **Retries.**
  - A next epoch that cannot be planned (m1) or started, and a service ending
    within a second, are retried after 1, 2, 4 … up to 30 seconds.
  - The wait is the main poll's timeout, so a stop request, retiring epochs and
    purges are answered meanwhile.
  - The new `epoch-N` is delegated only after `records` and the service leaf
    exist.
- **Clients while no current epoch runs (N5).** A helper's own connection
  reaches its retiring epoch. Up to 32 other clients are held until an epoch
  starts; the rest wait in the backlog.
- **Policy bounds (N6).** Per-record pids are capped at 2^22 and memory at
  64 TiB, so the limit products cannot wrap.
- **Not fixed, recorded as known limits:**
  - N3: quarantines keep what other IDs own;
  - N4: an NSS outage that reports ENOENT counts as "not found";
  - N7: a bind mount on the same filesystem;
  - N6: the nested-capacity rule is documented, not enforced.
- **Evidence.** The root protected acceptance meets 43 of 43 expectations in
  three consecutive runs.
  - Payload files inside another user's 1777 directories named like the
    quarantine, in `/var/tmp` and `/dev/shm`, are removed.

## U-20261030-21 · 2026-10-30 · Read every quarantine pass from the start, stop purges only on churn, and refuse set-ID bits · #snapshot #agent #linux #security

- A seventh independent review confirmed M2, m1, m3, N1, N2 and the overflow
  half of N6 fixed. It found two major problems:
  - **MAJOR-1.** Every quarantine pass `dup`ed the same descriptor, which
    shares its offset. Only the first pass read anything, so chains deeper
    than about two walks stayed in the quarantine, with their tmpfs pages,
    while the purge reported clean. This was already in U-20261030-19.
  - **MAJOR-2.** The entry budget of U-20261030-20 let any local user stop
    every slice for good with a large static tree (for example 4.2M hard
    links in `/var/tmp`).
- **Quarantine passes.** Each pass opens the quarantine afresh, so it reads
  from the first entry.
- **When a purge stops short.**
  - The budget is gone; the size of what others keep only makes a purge
    slower.
  - A purge now stops short only on churn a live user causes: a directory
    entered twice in one walk (a table of up to 2^22 directories), or a
    listing yielding far more entries than its size when opened.
  - What is walked is the directory actually opened, and its owner is read
    from it.
  - A payload directory that could not be moved into the quarantine, for any
    reason, makes the purge incomplete.
- **Concurrent purges (m-A).** Each quarantine is locked with `flock` while
  its purge runs, and a locked one at a root's top is left alone. Purges of
  two slices no longer remove each other's quarantine.
- **Deferral.** Another ID's directories at the depth bound are deferred up
  to 4096, or what the raised descriptor limit leaves room for. Beyond that
  the purge logs once and is not made incomplete.
- **Set-ID bits (m-B).** The service filter, which every payload inherits,
  refuses set-user- and set-group-ID bits from the chmod family, a creating
  open or mknod; `openat2` answers ENOSYS. A file that escapes a purge is
  data, not an identity.
- **Clients and loop (m-C, N-a).**
  - While no current epoch runs, the listener stays read for retiring
    epochs' helpers, and clients beyond the 32 held ones are dropped.
  - A slice waiting to be purged again with no purge child running wakes the
    loop every second.
- **Smaller fixes.**
  - N-b: `pids.max` above the kernel's 2^22 is written as `max`.
  - N-c: directories deferred inside a quarantine count as quarantined.
- **Known limits.** A live local user who renames another ID's directory
  behind the walk, or a payload file inside another ID's directories past the
  deferral limit, can escape one purge. Both need a directory that ID let the
  payload write into.
- **Evidence.** The root protected acceptance meets 43 of 43 expectations.
  - A 300-level chain in `/dev/shm` with 8 MiB at its bottom leaves its name

  - Another user's static tree with 5000 directories at the depth bound is

  - The filter probe refuses setuid and setgid through fchmod, fchmodat, a
