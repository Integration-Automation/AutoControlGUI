## U-20260922-03 · 2026-09-22 · hotkey/type_keyboard release held keys on failure · #incident #input

- **What**: `wrapper/auto_control_keyboard.py` — `hotkey` and `type_keyboard` now release from `finally` through `_release_still_held(still_held, is_shift)`. A key is recorded as held only after its press succeeded, so a key that never went down is never released (that would cancel a key the user is physically holding); release order is reverse press order; a release failing inside the cleanup is logged and the loop continues, and nothing is raised from `finally`.
- **Why `finally`, not a wider `except`**: the functions catch `(OSError, RuntimeError, AttributeError, TypeError, ValueError)`, and `AutoControlKeyboardException` (an `AutoControlException`) is under none of them, so the most likely failures skipped the `except` entirely. A test pins that premise.
- **Result / numbers**: `test/unit_test/headless/test_keyboard_release_on_failure.py`, 11 tests; mutating the cleanup to re-raise fails 3 of them. The cleanup-error test uses two distinct exception objects so identity shows which one reached the caller.

## U-20260922-12 · 2026-09-22 · 16 background services: a restart no longer revives the old loop · #incident #threading

- **What**: The bug fixed in the USB watcher (U-20260922-06) was a pattern, not a one-off. `grep "_stop.clear()"` found it in 16 more places, all shaped the same: `stop()` sets `self._stop`, joins with a timeout, drops the thread; `start()` calls `self._stop.clear()` and starts a new thread whose loop reads `self._stop`. A loop still inside a long iteration when the join timed out is revived by the next `start()` and runs beside the new one, untracked. Where the loop body acts, that doubles the action: `Scheduler._run` executes jobs inline, `HotkeyDaemon` fires bindings, `TriggerEngine` / `EmailTriggerWatcher` run action lists, `PopupWatchdog` clicks.
- **Fix**: one `threading.Event` per run, created in `start()` (never `clear()`ed) and passed to the loop as a required argument; `stop()` is unchanged and sets the current run's event. Files: `utils/{accessibility/recorder, clipboard_history/clipboard_history, mcp_server/plugin_watcher, observer/observer, profiler/resource_profiler, remote_desktop/file_sync, scheduler/scheduler, tls_acme/renewal, triggers/email_trigger, triggers/trigger_engine, usb/passthrough/loopback, watchdog/popup_watchdog}.py` (scripted, each replacement asserted to match once), `utils/hotkey/hotkey_daemon.py` (event goes through `BackendContext.stop_event`), `utils/usbip/server.py` (the accept loop hands its event on to every URB worker), `osx/listener/osx_listener.py`, `utils/chatops/slack_bot.py` (`run_forever` runs on the caller's thread).
- **Result / numbers**: new `test/unit_test/headless/test_background_restart_keeps_old_run_stopped.py`, 15 tests: each service's `threading` is swapped for a thread that never finishes (what `stop()` sees when the loop is stuck), and after stop → start the first run's event must still be set and the loop must have been handed it. ## U-20260922-14 · 2026-09-22 · Scheduler: never start a job that is still running · #incident #scheduler

- **What**: The residue of U-20260922-12 in `utils/scheduler/scheduler.py`. `_fire` updates `next_run_ts` / `runs` only after `self._execute(actions)` returns, so a job keeps looking due for as long as it runs.
