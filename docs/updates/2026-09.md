## U-20260922-02 · 2026-09-22 · Windows recorder captures mouse side buttons (x1/x2) · #incident #recording

- **What**: `Win32InputHook._mouse_event` now records `WM_XBUTTONDOWN` / `WM_XBUTTONUP` (0x020B / 0x020C) as `mouse_down` / `mouse_up` with `button` `"x1"` / `"x2"`. The button id lives in the high word of `mouseData` (like the wheel's notch count), so the message-id-keyed `_MOUSE_BUTTONS` table could not express it and side clicks were silently dropped. `_RECORDED_BUTTON` in `input_macro.py` gained `x1` / `x2` in the same change: its fallback for an unknown name is `mouse_left`, so emitting `x1` without the replay mapping would have turned a side click into a real left click. Unknown high-word values are dropped, not guessed, for the same reason.
- **Not changed**: `LEGACY_MOUSE_COMMAND` (the down-events-only `stop_record()` queue) still has no side buttons — there is no `AC_mouse_x1` executor alias, and naming one would fail at replay instead of at record. Comment added in `recorder_base.py`.
- **Result / numbers**: `test/unit_test/headless/test_input_hook_side_buttons.py`, 10 tests (press/release per button, the two buttons told apart, unknown value dropped, replay map covers every name the hook emits). Windows-only module; skips elsewhere.
- **Files**: `je_auto_control/windows/record/win32_input_hook.py`, `je_auto_control/utils/input_macro/input_macro.py`, `je_auto_control/utils/input_macro/recorder_base.py`, `CHANGELOG.md`, `architecture_explore.md` (line counts).
- **Open items**: none.

## U-20260922-03 · 2026-09-22 · hotkey/type_keyboard release held keys on failure · #incident #input

- **What**: `wrapper/auto_control_keyboard.py` — `hotkey` and `type_keyboard` now release from `finally` through `_release_still_held(still_held, is_shift)`. A key is recorded as held only after its press succeeded, so a key that never went down is never released (that would cancel a key the user is physically holding); release order is reverse press order; a release failing inside the cleanup is logged and the loop continues, and nothing is raised from `finally`.
- **Why `finally`, not a wider `except`**: the functions catch `(OSError, RuntimeError, AttributeError, TypeError, ValueError)`, and `AutoControlKeyboardException` (an `AutoControlException`) is under none of them, so the most likely failures skipped the `except` entirely. A test pins that premise.
- **Result / numbers**: `test/unit_test/headless/test_keyboard_release_on_failure.py`, 11 tests; mutating the cleanup to re-raise fails 3 of them. The cleanup-error test uses two distinct exception objects so identity shows which one reached the caller.
- **Files**: `je_auto_control/wrapper/auto_control_keyboard.py`, `CHANGELOG.md`, `architecture_explore.md` (§5.2 row, §7 note, line counts).
- **Open items**: none.
