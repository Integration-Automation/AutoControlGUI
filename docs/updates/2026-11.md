## U-20261101-06 · 2026-11-01 · Add macOS and X11 physical-activity sources · #snapshot #agent #presence #macos #x11

- **What.** The first step of `Progress.md` item 3's macOS/X11 bullet: a
  trusted physical-activity source for each platform, behind the same native
  API contract as `Win32PresenceAPI`. That contract is:
  - `open(physical)` and `poll(timeout)` on one owner thread;
  - `poll` waits at most 50 ms, drains at most 1,024 events (more is
    `AgentControlBusy`) and returns `(interactive, held)`;
  - `close` releases what the source owns.

  The existing `WindowsPresenceSource` loop and the sixty-second idle
  `PresenceState` run any of them, through the new `presence_platform.py`.
- **X11** (`presence_x11.py`).
  - It selects XInput2 raw key, button and motion events for every device on
    the root window, the only global XInput2 view, plus `HierarchyChanged`.
  - It parses the raw header itself (`=HIIHH`): python-Xlib 0.33 registers
    parsers only for device events, which reach focused windows, not for raw
    events.
  - Events from XTEST slaves never count as physical. A source that is not a
    slave device refreshes the device list and is then ignored.
  - `held` is tracked from physical press/release events, or-ed with the core
    keymap and pointer buttons, which errs toward held.
  - The seat is usable only when logind reports `Active=yes` and
    `LockedHint=no` for `XDG_SESSION_ID`. It is read through `loginctl` with a
    fixed argv, a 1-second timeout and a 1-second cache. Without logind or a
    session id, or on any failure, the seat counts as locked.
- **macOS** (`presence_quartz.py`).
  - A listen-only `kCGSessionEventTap`. Without the Accessibility permission
    `CGEventTapCreate` returns nothing and the source refuses to start.
  - Mistaking a person for an injection is the unsafe direction, so an event
    counts as injected only when `kCGEventSourceUnixProcessID` is positive
    *and* its source state is not the HID system state.
  - `held` adds HID-state key and button queries, for anything already down
    before the tap started.
  - A disabled tap (timeout or user input) fails the source.
  - The console is usable when `CGSessionCopyCurrentDictionary` is on console
    and not locked.
- **Wayland** stays without a source. `presence_backend` returns
  `unsupported` whenever `WAYLAND_DISPLAY` or `XDG_SESSION_TYPE=wayland` is
  set, because a client sees no global input and cannot tell a person from
  libei or uinput injection.
- **Not changed.** Non-Windows shared-desktop input stays refused: the
  presence worker still only has the Windows pipe, and helper launch, endpoint
  transfer and challenge/lease integration are still to come. Readiness now
  reports `presence_source` as `not_probed` for macOS and X11, with that
  refusal in its detail.

## U-20261101-11 · 2026-11-01 · Start the Android device-side helper with its fence ledger · #snapshot #agent #android

- **Why on the device.** `AndroidCommandLease` requires an old writer to stop
  after a takeover, expiry or cancellation. Each command must be settled by its
  own request id, boot and epoch, with input released and nothing left queued.
  A host lock, an `adb shell` return code or a local process exit proves none
  of that. Per the maintainer's choice, the helper is built here and built and
  tested in CI, since this machine has no JDK or Android SDK.
- **Stage 1 of 4.**
  - `native/android_helper/README.md` specifies protocol version 1: the
    `hello`, `fence`, `begin` and `settle` requests over the abstract socket
    `je_auto_control_helper` through `adb forward`, one bounded JSON object
    per line.
  - `core/` holds `FenceLedger`, the pure-Kotlin state machine every request
    goes through.
  - A command runs only under the epoch it was begun with.
  - `fence` moves the epoch forward for good: queued older commands become
    `fenced`, and an injecting one is told to stop between events. A command a
    fence overtook can never become `completed`.
  - It refuses a stale epoch, a reused id and a full queue. Only one command
    injects at a time. `settle` answers from the ledger alone, and an unknown
    id settles as `rejected`.
- **CI.** `.github/workflows/android-helper.yml` runs the JVM tests (JDK 17,
  Gradle 8.11.1, Kotlin 2.0.21, JUnit 4.13.2) when `native/android_helper/**`
  changes on `dev` or `main`, or in a pull request to `main`. It holds no
  secret and publishes nothing.
- **Not done.**
  - Stage 2: the instrumentation app (socket server and `UiAutomation`
    injector).
  - Stage 3: the host provider implementing `AndroidControlProvider`, with
    `getevent` as the physical-input source, since injected events never reach
    `/dev/input`.
  - Stage 4: emulator tests in CI.

  Nothing is wired into the runtime. Real-device acceptance stays deferred.
- **Open items.** `Progress.md` item 4.

## U-20261101-13 · 2026-11-01 · Run the Linux presence broker, worker and server over the owned Linux channel · #snapshot #agent #presence #linux

- **Why.** The X11 source (U-20261101-06) had no way to reach the runtime:
  the presence broker, the worker and its server were hardwired to the Windows
  named pipe and Windows peer security. Linux already had an authenticated
  packet channel (`presence_channel_linux.py`). Its endpoint, though, is a
  fresh private socket that a client may trust only when the endpoint came
  through a trusted launch.
- **What.** New `presence_pipe_linux.py`, shaped like the Windows pipe and
  security:

    it an endpoint.

    bounded receive or accept. `LinuxChannel` revokes itself when a bounded
    operation runs out of time, so a blocking wait inside one would kill the
    channel. Close cancels a wait first.
  - `endpoint_to_wire` and `endpoint_from_wire` carry the endpoint with closed
    fields, bounded integers, an absolute directory and a bounded socket name.
  - `LinuxPresenceSecurity` takes the peer from the connected socket's pidfd
    (`retain_connected_peer`), so the existing presence challenge compares
    process births.
- **The trusted launch path.**
  - `PresenceServer.start` adds the listener's endpoint to its owned bootstrap
    reply.
  - The broker accepts that reply shape, adopts the endpoint only from its own
    `SourceProcess`, and connects. `LinuxChannel.connect` then pins the actual
    listener to the process the endpoint names before the presence handshake.
  - `presence_platform` picks the transport, Linux or Windows. Windows
    construction is unchanged.
  - Two small additions to `presence_channel_linux.py`: `LinuxChannel.fileno()`
    and `LinuxListener.fileno()`, used for readiness waits and peer evidence.
- **Not changed.** `presence_reader` still uses only the Windows pipe, macOS
