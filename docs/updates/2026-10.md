## U-20261001-03 · 2026-10-01 · Tesseract setup helpers: find the engine, set tessdata, report status and languages · #feature #ocr #contract

Jeffrey_RPA's `_gui_control.py` imported `pytesseract` itself to list languages and check the engine, and wrote `pytesseract.pytesseract.tesseract_cmd` directly, so that module global had two writers. The library now answers those questions itself and `TesseractBackend.set_cmd` stays the only writer.

- **New module** `utils/ocr/tesseract_setup.py`, exported from the facade and `utils/ocr`:
  - `find_tesseract_cmd() -> Optional[str]`: `$TESSERACT_CMD` when it names a file, then `PATH`, then the installers' default folders (Windows `Program Files`, `Program Files (x86)`, `%LOCALAPPDATA%\Programs`; Homebrew, `/usr/local`, MacPorts; `/usr/bin`, `/usr/local/bin`). Looks only.
  - `set_tessdata_dir(path) -> Optional[str]`: realpath, must be a directory, sets `TESSDATA_PREFIX`; `None` removes it.
  - `ocr_languages() -> Optional[List[str]]`: sorted codes, `[]` when the engine answered with none, `None` when it could not be asked. Never cached.
  - `ocr_status() -> OCRStatus(ok, reason)`: `missing_package`, `missing_engine` (the configured command is neither on `PATH` nor a file), `engine_unusable`, `no_language_data` (only for an answered empty list), else `ready`. Checks the command OCR would use and configures nothing.
- **Backend**: `TesseractBackend.cmd`, `version()` and `languages()`, each raising `OCRBackendNotAvailableError` when the engine cannot run. `version()` also catches the `SystemExit` pytesseract raises for a version string it cannot parse, which would otherwise end the calling process.
- **Surfaces**: `AC_ocr_status` → `{ok, reason}`, `AC_ocr_languages` → `{languages}` (`null` when unknown), the matching `ac_ocr_status` / `ac_ocr_languages` MCP tools (read-only) and two Script Builder entries. 776 commands, 679 MCP tools.
- **Real engine** (this host, read-only probe): `ocr_status()` gave `missing_engine` before configuration; `find_tesseract_cmd()` found `C:\Program Files\Tesseract-OCR\tesseract.exe` (not on `PATH`); after `set_tesseract_cmd` it gave `ready`, `ocr_languages()` listed `eng`, `osd`, and after `set_tessdata_dir` on a folder with three language files it listed those three.
- **Tests**: new `test_ocr_tesseract_setup.py` (27 tests, fake pytesseract): `None` versus `[]`, no caching, each status reason including `SystemExit`, one writer for the command, tessdata validation, every lookup step, the executor, MCP and Script Builder wiring. `test_cross_project_contracts.py` pins the four names for Jeffrey_RPA.
- **Docs**: `docs/source/{Eng,Zh}/doc/ocr_backends/ocr_backends_doc.rst` (setup notes, JSON surface, diagnostics), `README.md` and both translations (install note, OCR row, counts), `architecture.md` §6, `architecture_explore.md` (OCR rows, counts, re-measured lines), `je_auto_control/actions.pyi` regenerated (which also picks up the drifted signatures of `AC_queue_complete`, `AC_queue_fail` and `AC_shell_command`, and re-escapes one docstring quote), `CHANGELOG.md`.

## U-20261001-04 · 2026-10-01 · click_mouse(clicks=, interval=): a double-click in one call · #feature #input

Jeffrey_RPA double-clicked with two `click_mouse` calls and its own sleep. The wrapper now does it in one call.

- **Signature**: `click_mouse(mouse_keycode, x=None, y=None, clicks=1, interval=0.0)` in `wrapper/auto_control_mouse.py`. The point is resolved once and every click lands on it; `time.sleep(interval)` runs only between clicks and only when `interval` is non-zero. Defaults are the old single click, and a single click records the same `click_mouse` action as before (the `clicks` / `interval` keys appear only when used).
- **Validation** (`_click_plan`, raising `AutoControlMouseException` before any click): `clicks` is an int or integer string, at least 1, never a `bool` or a float (a float would be truncated silently); `interval` is finite and at least 0 (NaN passes a plain `< 0` test).
- **Surfaces**: `AC_click_mouse` is the wrapper itself, so action files get both parameters; the `ac_click_mouse` MCP tool and its handler, the MCP fake backend (one recorded click per click) and the Script Builder fields follow. `je_auto_control/actions.pyi` regenerated.
- **macOS**: apps there read a click count the osx backend never sets, so `clicks=2` arrives as two single clicks. Documented in the docstring and docs, and recorded in `Progress.md`.
- **Tests**: new `test_click_mouse_multi.py` (22 tests, stand-in backend and clock): the unchanged default and its record, the double-click and its single pause, no pause at `interval=0`, macOS argument order on every click, each refused `clicks` / `interval` value clicking nothing, and the executor, MCP handler, fake backend, MCP schema and Script Builder wiring.
- **Docs**: `docs/source/API/wrapper/mouse.rst`, `docs/source/{Eng,Zh}/doc/mouse/mouse_doc.rst`, the Mouse row of `README.md` and both translations, `CHANGELOG.md`; `architecture.md` §6 lists the two keywords for Jeffrey_RPA and `test_cross_project_contracts.py` pins them.

## U-20261001-05 · 2026-10-01 · Drag pacing for tween_drag / drag_path; an aborted drag lets go where it stopped · #feature #bugfix #input

Jeffrey_RPA kept its own drag loop because the library's drags moved as fast as the events could be sent, which apps that judge a drag by the pointer's motion read as a click, and because an aborted drag released the button at the drop target.

- **Shared sequence**: `utils/tween_drag/tween_drag.py` `_drag_through(points, button, dispatch, step_delay_s, settle_s)` now holds the press / move / release for both `tween_drag` and `mouse_path.drag_path`, which previously had two copies of the same loop.
- **Pacing**: `step_delay_s` rests after each move; `settle_s` (when non-zero) moves to the start and rests before the press, then rests after the press and before the release. Both default to 0, where the events are exactly press, moves, release with no sleep, as before. NaN, infinities, negatives and non-numbers raise `ValueError` before anything is dispatched (a NaN reaching `time.sleep` would raise with the button held).
- **Release on failure**: after the press, a `held` flag and a `finally` (the pattern of `hotkey` / `type_keyboard` and `_release_still_held`) release the button at the last point the pointer reached when any step raises, `KeyboardInterrupt` included. It used to release at the last point of the path, completing a drop the drag never reached. The cleanup release never raises over the original error (logged instead); a failing final release propagates after one cleanup retry, as `hotkey` does. A failed press releases nothing.
- **Surfaces**: the `AC_tween_drag` / `AC_drag_path` adapters, the `ac_tween_drag` / `ac_drag_path` MCP tools and handlers (`_handlers_executor_bridge.py` kept its line count, as its `Progress.md` ceiling requires) and the Script Builder fields take both. `je_auto_control/actions.pyi` regenerated.
- **Signatures**: `tween_drag(start, end, *, steps=30, easing="ease_in_out_quad", button="mouse_left", sink=None, step_delay_s=0.0, settle_s=0.0)` and `drag_path(waypoints, *, button="mouse_left", easing="linear", per_segment_steps=20, sink=None, step_delay_s=0.0, settle_s=0.0)`. `tween_drag` now has eight parameters, one over the `CLAUDE.md` review limit; all are keyword-only after `start` / `end`, and `wait_for_text` already has eight.
- **Tests**: new `test_drag_pacing.py` (25 tests, recording sink and clock): unchanged defaults for both drags, the pause order for each setting, every refused value sending nothing, release at the last reached point (mid-path, first move, interrupted pause), no release after a failed press, a failing cleanup not hiding the original error, the final-release retry, and the executor, MCP and Script Builder wiring. The existing drag tests pass unchanged.
- **Docs**: `docs/source/{Eng,Zh}/doc/new_features/v29_features_doc.rst` and `v116_features_doc.rst`, the Mouse row of `README.md` and both translations, `architecture.md` §6 (with `test_cross_project_contracts.py` pinning the keywords), `architecture_explore.md` (tween_drag row, the `finally` section, re-measured lines), `CHANGELOG.md` (Added and Fixed).
- **Open items**: none.

## U-20261001-06 · 2026-10-01 · Windows OEM keys, browser_home, launch_app2 and key aliases; canonical reverse lookup · #feature #input #contract

Jeffrey_RPA kept its own `KEY_ALIASES` (40 friendly names) and `_EXTRA_KEY_CODES` (16 keys the library could not name: the OEM keys, `browser_home`, and `launch_app2`, which existed only upper-case) and converted names to codes before every call. The Windows table now has all of them, with the same names and codes.

- **Table** (`wrapper/_platform_windows.py`, constants in `windows/core/utils/win32_vk.py`): `oem_1` .. `oem_8`, `oem_102`, `oem_plus`, `oem_comma`, `oem_minus`, `oem_period`, `oem_clear`, `browser_home` (0xAC) and `launch_app2` (0xB7) beside the old `LAUNCH_APP2`. Codes checked against Microsoft's "Virtual-Key Codes". Layout-dependent OEM keys keep Microsoft's names; a character name such as `semicolon` would be wrong on other layouts.
- **Aliases**: one map, `keyboard_key_aliases` (alias → canonical name; the `"ctrl"` entry moved there from the table literal), merged into the table after the canonical names. Every platform module and `platform_wrapper` publish the map (empty off Windows). 230 names on Windows, 40 of them aliases (was 175 names).
- **Reverse lookup**: new `keyboard_key_name(keycode) -> Optional[str]` in `wrapper/auto_control_keyboard.py`, exported from the facade. Aliases never answer. Among the rest a typable name (`[a-z0-9_]+`) wins, then the shortest, then alphabetical order. For every code the old table already named, it returns exactly what a shortest-lower-case lookup over the pre-alias table returned (`control`, `return`, `escape`, `lwin`, `snapshot`, `num0`, `down`, `a`, ...). The new keys get their new names (`launch_app2`, not `LAUNCH_APP2`).
- **Jeffrey_RPA's current `_vk_to_name`** takes the shortest name from the raw table and then maps it through its own aliases. Simulated over VK 1-254 against both tables, it changes for one key: VK 0x2C writes `prtsc` instead of `printscreen`. Both names are the same key and validate and replay identically. Its modifier keys never reach the table. Calling `keyboard_key_name`, or skipping `keyboard_key_aliases`, removes the difference. Its `test_every_code_the_library_can_name_can_also_be_written` positive control ("the real table still has a key named only in upper case") stops holding once `launch_app2` exists in lower case. That test's own message says to revisit the premise in that case.
- **Tests**: new `test_key_names_and_aliases.py` (68 tests; the table checks run on Windows): Microsoft codes for the 16 added keys, the upper-case spelling kept, every alias resolving through `_resolve_keycode` to its target's code, no alias pointing at another alias or at a layout-dependent key, the pre-alias canonical name for every aliased code, an alias-free answer for every code in the table, the preference order on a synthetic table (runs everywhere), and the facade export. `test_cross_project_contracts.py` pins `keyboard_key_name`, `keyboard_key_aliases` and the names Jeffrey_RPA uses.
- **Docs**: `docs/source/API/special/keyboard_keys.rst` (the Windows list rewritten to names that exist, with aliases, OEM and launch keys; it listed `print_screen`, `lalt` and `numpad0`, which did not exist), `docs/source/API/wrapper/keyboard.rst`, `docs/source/{Eng,Zh}/doc/keyboard/keyboard_doc.rst`, the Keyboard row of `README.md` and both translations, `architecture.md` §6, `architecture_explore.md` (two rows, public-API and test counts re-measured, lines), `CHANGELOG.md` (Added and Changed).
