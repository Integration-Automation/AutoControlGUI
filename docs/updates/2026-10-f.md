## U-20261031-01 · 2026-10-31 · Build the agent schema in one transaction, and stop a racing resolve from reading as an escape · #incident #agent #ci #windows

- **What failed.** The first Dev CI runs after `dev` took the agent runtime
  (41183049249, 41185824279) were red on every square:
  - Linux and macOS: `test_doc_line_counts.py` found 7 stale line counts in
    `architecture_explore.md` after `native_channel.py` grew.
  - Both Windows squares hit the 30-minute job limit at about 27% of the suite
    (4,719 of ~16,700 tests). The agent tests ran about 15 times slower there
    than on Linux, and 4.5 times slower when measured file by file.
- **Schema in one transaction.** `AgentTaskStore` connects in autocommit mode,
  so its 44-statement `_SCHEMA` ran as 44 transactions, each with its own sync,
  once per store instance. It now runs between `BEGIN IMMEDIATE` and `COMMIT`.
  That is one sync, and a failure part-way leaves no half-created schema
  (the existing handler rolls the open transaction back). Locally
  `executescript` went from 4.5 s to 0.38 s over `test_agent_runtime.py` and
  `test_agent_dag_batches.py` (10.0 s to 4.8 s for both files).
- **That is not what makes Windows slow.** On the five slowest files on CI the
  same change saved 4% locally (168 s to 161 s). The store opens a new SQLite
  connection, with a `mkdir` and a `chmod`, for every operation:
  `test_agent_evidence_handoff_security.py` alone opens 8,206 across 30 tests.
  Projected from the per-file Linux times, a Windows square needs about 80
  minutes. → `Progress.md`.
- **A racing resolve read as an escape.**
  `test_agent_evidence_cache_transactions.py::test_competing_first_ensures_create_one_current_segment`
  failed in 2 of 5 local runs, with and without the schema change. When one
  thread checks a task directory while another creates it, `ntpath.realpath`
  can see the path missing, find it during its non-strict walk, and then fail
  to reopen it to strip the `\\?\` prefix. It returns `\\?\C:\...`, so
  `path.resolve() != path` raised "task artifact directory escapes its owner
  cache". A probe at the failing moment showed `exists() == False` while
  `lstat` reported a directory.
  - New `utils/agent_runtime/path_identity.py`: `resolved()` returns
    `path.resolve()` in the spelling of `path`. It drops only the `\\?\` prefix
    of a drive or UNC path, only on Windows, and only when `path` was not spelled
    with it.
  - All eight `resolve() != path` identity checks in `agent_runtime` use it:
    `evidence_cache` (2), `policy`, `transfer_cache`, `transfer_files`,
    `transfer_import_files` (2) and `transfer_staging`.
- **Evidence.**
  - The racing test passes 12 of 12 locally (before: 3 of 5).
  - `test_agent_path_identity.py`: 10 tests. A prefixed resolution of the same
    path is accepted, and a prefixed resolution to another place is still
    refused.
  - 852 agent evidence, transfer, policy, origin, store and runtime tests pass.
  - The doc, file-length, complexity and broad-except gates pass. ruff, bandit
    and radon report nothing on the touched files.
- **Open items.** The Windows Dev CI time limit: see `Progress.md`.

## U-20261031-02 · 2026-10-31 · Give the Dev CI squares a 120-minute limit · #decision #ci #windows

- **Decided by the maintainer:** raise `timeout-minutes` of `pytest-headless`
  in `.github/workflows/dev.yml` from 30 to 120, rather than shard the Windows
  squares or make `AgentTaskStore` reuse connections.
- **Why the limit, not the code.** U-20261031-01 measured the cost: a fresh
  SQLite connection, `mkdir` and `chmod` per store operation. That is about
  80 minutes per Windows square. Linux and macOS take about 25 minutes, close to
  the old limit. Reusing connections would change the store's concurrency
  semantics, which needs its own review.
- **Cost:** a push to `dev` now waits about 80 minutes before
  `je_auto_control_dev` is published. `quality.yml` has no limit, so the pull
  request to `main` was never affected.
- **Open items:** none. U-20261031-01's pointer to `Progress.md` is answered
  here.

## U-20261031-03 · 2026-10-31 · Cap the helper's retirement deadline, and keep one failed fixture from spreading · #incident #agent #ci #windows

- **Run.** Dev CI 41199447801 on `649aab3b`, the first in which every square
  ran the whole suite. Linux 3.14 and macOS 3.10 passed (jobs of 25 and 24
  minutes).
- **Correction to U-20261031-02.** The Windows suites took 43:00 (3.10) and
  47:55 (3.14), in jobs of 45 and 49 minutes, not the projected 80. The 120-minute
  limit stays; the `dev.yml` comment now quotes the measured times.
- **Windows 3.10: 66 failed, 10 errors, from one cause.**
  - `OwnedChannel._stop_process` sets `deadline = time.monotonic() + 3` and
    passes `max(0, deadline - time.monotonic())` to `NativeJob.close`, which
    refuses anything over 3. Python 3.10 on Windows reads a millisecond clock,
    so both reads often return the same value. Where `t + 3` crosses a power of
    two, `(t + 3) - t` rounds to just over 3 (`32765.838` gives
    `3.000000000003638`), and the Job refused the deadline
    (`native retirement deadline must be finite and between0and3`).
  - It happened inside the `renewal` fixture of
    `test_agent_completion_authorization.py`. Its teardown ran `runtime.close()`,
    which raised the same error, and `scopes.close()` never ran. That left the
    owner's `AuthorizationContext` active for the rest of the session, and the
    later failures are all that context: unexpected `AuthorizationError`s and
    `AuthorizationContext(user_id='owner', ...) is None` assertions.
  - **Fix.** The timeout handed to the Job is capped at 3
    (`native_channel.py`). The new test
    `test_a_rounded_remaining_time_never_exceeds_the_jobs_three_second_bound`
    replays that clock reading.
  - The same teardown shape, `runtime.close()` followed by `scopes.close()`
    with nothing between, was in seven fixtures. All seven now close the scopes
    in a `finally`.
- **Windows 3.14: 1 failed.**
  `test_agent_dag_retention.py::test_completed_batch_keeps_its_gate_when_related_work_is_unsettled[held]`.
  The shared `task()` helper waits 2 seconds, and the managed task took 2.19.
  The retention tests now give their graph 20 seconds. The shared helper keeps
  2, because tests that expect a task not to finish would each wait the longer
  time.
- **Evidence.** The 85 tests of the touched fixtures, the native job and
  channel tests, and the doc gates pass. All 18 retention tests pass. ruff
  reports nothing.
- **Open items:** none.
